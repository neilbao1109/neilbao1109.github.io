# 公钥与私钥的应用详解

## 一、基本概念回顾

```
┌─────────────────────────────────────────────────┐
│                非对称密钥对                        │
│                                                   │
│   公钥 (Public Key)  ←→  私钥 (Private Key)      │
│   • 可以公开给任何人       • 必须严格保密           │
│   • 用于加密/验签         • 用于解密/签名           │
│   • 数学上由私钥推导       • 无法从公钥反推          │
└─────────────────────────────────────────────────┘
```

### 核心原则

```
公钥加密 → 私钥解密    （保证机密性）
私钥签名 → 公钥验签    （保证身份认证、完整性、不可否认性）
```

### 应用一：加密通信（Encryption）

> **目的**：确保只有接收者能读取消息

```
场景：Alice 要给 Bob 发送机密信息

                Alice                              Bob
                  │                                 │
                  │     ① Bob 公布自己的公钥          │
                  │ ◄─────────────────────────────── │
                  │                                  │
  ② 用 Bob的公钥  │                                  │
     加密明文     │     ③ 发送密文                    │
     M → C       │ ──────────────────────────────► │
                  │                                  │ ④ 用 Bob的私钥
                  │                                  │    解密密文
                  │                                  │    C → M
```

```
加密：C = Encrypt(M, Bob的公钥)     ← 任何人都能做
解密：M = Decrypt(C, Bob的私钥)     ← 只有Bob能做
```

#### 实际场景举例

**场景1：发送加密邮件 (PGP/GPG)**
```
1. Bob 将公钥发布到密钥服务器
2. Alice 从服务器获取 Bob 的公钥
3. Alice 用 Bob 公钥加密邮件内容
4. 密文通过互联网传输（即使被截获也无法阅读）
5. Bob 用自己的私钥解密，得到原文
```

**场景2：混合加密（实际中最常用）**

由于非对称加密速度慢，实际中采用混合方案：

```
发送方 Alice：
┌──────────────────────────────────────────┐
│ ① 随机生成对称密钥 K（如 AES-256 密钥）    │
│ ② 用 K 对明文进行对称加密：                 │
│      C_data = AES_Encrypt(明文, K)         │
│ ③ 用 Bob 的公钥加密 K：                     │
│      C_key = RSA_Encrypt(K, Bob公钥)       │
│ ④ 发送 (C_key, C_data)                     │
└──────────────────────────────────────────┘

接收方 Bob：
┌──────────────────────────────────────────┐
│ ① 用私钥解密得到对称密钥：                   │
│      K = RSA_Decrypt(C_key, Bob私钥)       │
│ ② 用 K 对称解密得到明文：                    │
│      明文 = AES_Decrypt(C_data, K)          │
└──────────────────────────────────────────┘
```

> 这就是 **HTTPS、SSH、PGP** 等协议的核心工作方式。

### 应用二：数字签名（Digital Signature）

> **目的**：证明消息确实由声称的发送者发出，且未被篡改

```
场景：Alice 要向 Bob 证明一份文件确实是她发出的

          Alice                                    Bob
            │                                       │
 ① 对文件计算哈希                                    │
    H = Hash(文件)                                   │
            │                                       │
 ② 用Alice私钥对哈希签名                              │
    Sig = Sign(H, Alice私钥)                         │
            │                                       │
            │    ③ 发送（文件 + 签名Sig）              │
            │ ────────────────────────────────────► │
            │                                       │
            │                          ④ 对收到的文件计算哈希
            │                             H' = Hash(文件)
            │                                       │
            │                          ⑤ 用Alice公钥验证签名
            │                             H'' = Verify(Sig, Alice公钥)
            │                                       │
            │                          ⑥ 比较 H' == H''
            │                             相等 → 签名有效 ✓
            │                             不等 → 签名无效 ✗
```

#### 数字签名提供的三大保证

```
┌─────────────────────────────────────────────────────┐
│ 1. 身份认证 (Authentication)                          │
│    → 只有 Alice 拥有私钥，所以签名只能是 Alice 生成的    │
│                                                       │
│ 2. 数据完整性 (Integrity)                              │
│    → 文件被篡改后，哈希值改变，签名验证必然失败            │
│                                                       │
│ 3. 不可否认性 (Non-repudiation)                        │
│    → Alice 不能否认签过名，因为只有她的私钥能生成该签名    │
└─────────────────────────────────────────────────────┘
```

#### 实际场景举例

**场景1：软件发布签名**
```
微软/苹果发布软件更新时：
1. 开发者用私钥对安装包签名
2. 用户下载后，操作系统用开发者公钥验证签名
3. 签名有效 → 确认是官方发布，未被篡改
4. 签名无效 → 警告用户"来源不可信"
```

**场景2：Git Commit 签名**
```bash
# 用 GPG 私钥签名 commit
git commit -S -m "Release v2.0"

# 验证 commit 签名
git log --show-signature
# 输出：Good signature from "Alice <alice@example.com>"
```

**场景3：电子合同/电子发票**
```
1. 合同双方各自用私钥对合同签名
2. 签名绑定了签名者身份 + 合同内容
3. 任何一方篡改合同，签名验证失败
4. 法律效力等同于手写签名（在很多国家）
```

### 应用三：TLS/HTTPS 安全通信

> **目的**：在浏览器和服务器之间建立安全加密通道

#### TLS 1.2 握手全过程

```
浏览器 (Client)                              服务器 (Server)
      │                                          │
      │ ──── ① ClientHello ────────────────────► │
      │      (支持的加密套件、随机数R_c)            │
      │                                          │
      │ ◄─── ② ServerHello ────────────────────  │
      │      (选定的加密套件、随机数R_s)            │
      │                                          │
      │ ◄─── ③ Certificate ────────────────────  │
      │      (服务器证书，包含公钥)                  │
      │                                          │
      │      ④ 验证证书                            │
      │      • 检查证书是否由可信CA签发              │
      │      • 检查证书是否过期                     │
      │      • 检查域名是否匹配                     │
      │                                          │
      │      ⑤ 生成预主密钥(Pre-Master Secret)     │
      │         用服务器公钥加密                     │
      │ ──── ⑥ ClientKeyExchange ──────────────► │
      │      (加密后的预主密钥)                      │
      │                                          │
      │                          ⑦ 用私钥解密得到预主密钥
      │                                          │
      │  ⑧ 双方用 R_c + R_s + 预主密钥             │
      │     推导出相同的会话密钥(Session Key)        │
      │                                          │
      │ ◄══════ ⑨ 后续通信用会话密钥对称加密 ══════► │
      │           (AES-256-GCM 等)                │
```

#### 在 TLS 中公钥私钥的角色

```
┌─────────────────────────────────────────────────────────┐
│ 公钥的角色：                                               │
│   1. 包含在数字证书中，发送给客户端                          │
│   2. 客户端用它加密预主密钥（密钥交换）                       │
│   3. 客户端用它验证服务器的签名（身份认证）                    │
│                                                           │
│ 私钥的角色：                                               │
│   1. 保存在服务器上，绝不传输                                │
│   2. 解密客户端发来的预主密钥                                │
│   3. 对握手消息签名，证明服务器身份                           │
└─────────────────────────────────────────────────────────┘
```

#### TLS 1.3 改进（ECDHE）

```
TLS 1.3 强制使用前向安全的密钥交换：

Client                                    Server
   │                                        │
   │  各自生成临时 ECDH 密钥对                 │
   │  (a, aG)                    (b, bG)    │
   │                                        │
   │ ──── ClientHello + aG ──────────────► │
   │ ◄─── ServerHello + bG + 证书签名 ────  │
   │                                        │
   │  共享密钥 = abG                         │
   │  服务器用长期私钥签名证明身份              │
   │  临时密钥用完即弃                        │
   │                                        │
   │  即使服务器长期私钥将来泄露，              │
   │  过去的通信也无法被解密                    │
   │  → 这就是"前向安全" (Forward Secrecy)   │
```

### 应用四：数字证书与 PKI 体系

> **目的**：解决"公钥属于谁"的信任问题

#### 核心问题：中间人攻击

```
没有证书时的危险：

Alice                   Mallory(中间人)              Bob
  │                          │                        │
  │  "我要Bob的公钥"          │                        │
  │ ───────────────────────► │                        │
  │                          │  把自己的公钥冒充Bob的    │
  │ ◄─── Mallory的公钥 ────  │                        │
  │                          │                        │
  │  用"Bob的公钥"加密         │                        │
  │  (实际是Mallory的公钥)     │                        │
  │ ──── 密文 ──────────────►│                        │
  │                          │ 用Mallory私钥解密        │
  │                          │ 读取/篡改内容            │
  │                          │ 用Bob真正的公钥重新加密   │
  │                          │ ──── 密文 ────────────► │
  │                          │                        │
  Alice和Bob都不知道通信被窃听和篡改了！
```

#### 解决方案：数字证书

```
┌──────────────────────────────────────────────┐
│              X.509 数字证书                     │
│                                                │
│  版本号：v3                                     │
│  序列号：03:A1:B2:...                           │
│  签名算法：SHA256withRSA                         │
│  颁发者：DigiCert Global Root CA               │
│  有效期：2024-01-01 至 2025-01-01              │
│  主体：CN=www.example.com                      │
│  主体公钥：30:82:01:0A:02:82:01:01:...        │
│  扩展：                                        │
│    - SAN: www.example.com, example.com         │
│    - Key Usage: digitalSignature, keyEncipherment│
│  ─────────────────────────────────────         │
│  CA的数字签名：                                  │
│    Sign(上述所有内容的哈希, CA的私钥)              │
│  签名值：4A:B3:C5:...                           │
└──────────────────────────────────────────────┘
```

#### PKI 信任链

```
Root CA（根证书颁发机构）
│  自签名证书，预装在操作系统/浏览器中
│  私钥离线保存在硬件安全模块(HSM)中
│
├── Intermediate CA（中间CA）
│   │  由 Root CA 签发证书
│   │
│   ├── www.google.com 的证书
│   │     由 Intermediate CA 签发
│   │
│   ├── www.github.com 的证书
│   │     由 Intermediate CA 签发
│   │
│   └── www.example.com 的证书
│         由 Intermediate CA 签发
│
└── 另一个 Intermediate CA
    │
    └── ...
```

#### 证书验证过程

```
浏览器收到 www.example.com 的证书后：

步骤1：提取证书链
   └─ 网站证书 → 中间CA证书 → 根CA证书

步骤2：从根开始逐级验证签名
   ┌─────────────────────────────────────────────────┐
   │ ① 根CA证书是否在浏览器信任列表中？                   │
   │    → 是 ✓（操作系统预装了约 100+ 根证书）            │
   │                                                   │
   │ ② 用根CA公钥验证中间CA证书的签名                     │
   │    Verify(中间CA证书签名, 根CA公钥) → 有效 ✓         │
   │                                                   │
   │ ③ 用中间CA公钥验证网站证书的签名                      │
   │    Verify(网站证书签名, 中间CA公钥) → 有效 ✓         │
   │                                                   │
   │ ④ 检查网站证书域名是否匹配                           │
   │    证书中 CN/SAN = www.example.com                  │
   │    实际访问域名 = www.example.com → 匹配 ✓           │
   │                                                   │
   │ ⑤ 检查证书是否过期 → 未过期 ✓                        │
   │                                                   │
   │ ⑥ 检查证书是否被吊销（CRL/OCSP）→ 未吊销 ✓          │
   │                                                   │
   │ 全部通过 → 显示 🔒 安全锁图标                        │
   └─────────────────────────────────────────────────┘
```

## 三、更多应用场景

### 应用五：SSH 免密登录

```
┌─ 一次性设置 ─────────────────────────────────────┐
│                                                    │
│  本地生成密钥对：                                    │
│  $ ssh-keygen -t ed25519                           │
│  → 私钥：~/.ssh/id_ed25519        (本地保存)       │
│  → 公钥：~/.ssh/id_ed25519.pub    (上传到服务器)    │
│                                                    │
│  将公钥添加到服务器：                                │
│  $ ssh-copy-id user@server                         │
│  → 追加到服务器 ~/.ssh/authorized_keys              │
└──────────────────────────────────────────────────┘

┌─ 每次登录 ───────────────────────────────────────┐
│                                                    │
│  Client                           Server           │
│    │                                │              │
│    │ ── "我要登录，我是 user" ────► │              │
│    │                                │              │
│    │ ◄── 发送随机挑战 challenge ──  │              │
│    │                                │              │
│    │  用私钥对 challenge 签名        │              │
│    │ ── signature ────────────────► │              │
│    │                                │              │
│    │              用 authorized_keys 中的公钥验签    │
│    │              验证通过 → 允许登录                │
│    │                                │              │
│    │ ◄── "登录成功" ────────────── │              │
└──────────────────────────────────────────────────┘
```

> 私钥从未离开本地机器，极大提高安全性。

### 应用六：加密货币（比特币/以太坊）

```
┌─ 钱包 = 密钥对 ─────────────────────────────────┐
│                                                    │
│  私钥：256位随机数                                   │
│    → 5HueCGU8rMjxEXxiPuD5BDku4MkFqeZyd4dZ1jvhTVqvbTLvyTJ │
│    → 掌握私钥 = 拥有比特币（"Not your keys, not your coins"）│
│                                                    │
│  公钥：由私钥通过椭圆曲线 secp256k1 计算              │
│    → Q = dG (d为私钥，G为基点)                       │
│                                                    │
│  地址：由公钥经过 SHA256 + RIPEMD160 + Base58Check   │
│    → 1A1zP1eP5QGefi2DMPTfTL5SLmv7DivfNa            │
│                                                    │
│  私钥 → 公钥 → 地址    (单向，不可逆)                │
└──────────────────────────────────────────────────┘
```

```
┌─ 比特币交易签名 ────────────────────────────────┐
│                                                    │
│  Alice 要发送 1 BTC 给 Bob：                       │
│                                                    │
│  ① 构造交易：                                      │
│     输入：Alice 的 UTXO（未花费交易输出）             │
│     输出：Bob 的地址 + 1 BTC                        │
│                                                    │
│  ② 用 Alice 的私钥对交易签名：                       │
│     Sig = ECDSA_Sign(交易哈希, Alice私钥)           │
│                                                    │
│  ③ 广播交易到比特币网络：                            │
│     (交易内容 + 签名 + Alice公钥)                    │
│                                                    │
│  ④ 矿工/节点验证：                                  │
│     ECDSA_Verify(交易哈希, Sig, Alice公钥) → ✓     │
│     确认 Alice 确实授权了这笔转账                     │
│                                                    │
│  ⑤ 交易被打包进区块，写入区块链                      │
└──────────────────────────────────────────────────┘
```

### 应用七：代码签名

```
┌─ Android APK 签名 ──────────────────────────────┐
│                                                    │
│  开发者：                                          │
│  ① 用私钥对 APK 中每个文件的哈希签名                  │
│  ② 签名信息存储在 META-INF/ 目录中                   │
│                                                    │
│  Android 系统安装时：                                │
│  ① 提取签名和公钥证书                                │
│  ② 验证 APK 中所有文件的签名                         │
│  ③ 签名有效 → 允许安装                              │
│  ④ 更新时检查新旧 APK 签名证书一致性                   │
│     (防止恶意替换应用)                                │
└──────────────────────────────────────────────────┘
```

```
┌─ macOS / iOS 代码签名 ──────────────────────────┐
│                                                    │
│  Apple 的多层签名体系：                              │
│                                                    │
│  ① 开发者用 Apple 颁发的证书签名 App                  │
│  ② App Store 审核后，Apple 再次签名                   │
│  ③ 设备启动时验证内核签名（Secure Boot）               │
│  ④ 运行时验证每个 App 的签名                          │
│  ⑤ 签名无效 → 拒绝运行                              │
└──────────────────────────────────────────────────┘
```

### 应用八：安全启动（Secure Boot）

```
设备开机流程中的签名验证链：

┌──────────────────────────────────────────────┐
│  硬件 ROM 中固化的公钥（不可修改）                │
│          │                                     │
│          ▼                                     │
│  验证 Bootloader 签名 ─── 失败 → 拒绝启动       │
│          │ 成功                                 │
│          ▼                                     │
│  验证 内核(Kernel) 签名 ── 失败 → 拒绝启动       │
│          │ 成功                                 │
│          ▼                                     │
│  验证 驱动程序 签名 ────── 失败 → 拒绝加载       │
│          │ 成功                                 │
│          ▼                                     │
│  验证 应用程序 签名 ────── 失败 → 拒绝运行       │
│          │ 成功                                 │
│          ▼                                     │
│  系统正常运行 ✓                                  │
│                                                │
│  → 整条链路确保从硬件到软件完全可信                │
│  → 防止 rootkit、bootkit 等底层恶意软件           │
└──────────────────────────────────────────────┘
```

### 应用九：电子邮件加密与签名 (S/MIME & PGP)

```
┌─ 同时加密+签名的邮件 ───────────────────────────┐
│                                                    │
│  发送方 Alice → 接收方 Bob：                        │
│                                                    │
│  ① 签名（确保来源和完整性）：                        │
│     H = SHA256(邮件正文)                            │
│     Sig = Sign(H, Alice的私钥)                     │
│                                                    │
│  ② 加密（确保机密性）：                              │
│     K = 随机生成 AES 会话密钥                        │
│     C_body = AES_Encrypt(邮件正文 + Sig, K)         │
│     C_key = RSA_Encrypt(K, Bob的公钥)               │
│                                                    │
│  ③ 发送：(C_key, C_body)                           │
│                                                    │
│  接收方 Bob：                                       │
│  ① K = RSA_Decrypt(C_key, Bob的私钥)               │
│  ② 邮件正文 + Sig = AES_Decrypt(C_body, K)          │
│  ③ Verify(Sig, Alice的公钥) → ✓                    │
│                                                    │
│  结果：                                             │
│  ✓ 只有 Bob 能阅读（机密性）                         │
│  ✓ 确认来自 Alice（身份认证）                        │
│  ✓ 内容未被篡改（完整性）                            │
│  ✓ Alice 不能否认发送（不可否认性）                   │
└──────────────────────────────────────────────────┘
```

### 应用十：零知识证明中的应用

```
┌─ 简化示例：证明"我知道私钥"而不泄露私钥 ──────────┐
│                                                     │
│  场景：Alice 要向 Bob 证明她拥有某公钥对应的私钥      │
│        但不希望泄露私钥的任何信息                      │
│                                                     │
│  Alice (Prover)              Bob (Verifier)         │
│     │                            │                  │
│     │                            │ 发送随机挑战 c    │
│     │ ◄──────────────────────── │                  │
│     │                            │                  │
│     │ 用私钥计算响应 r            │                  │
│     │ (包含c和私钥的某种数学运算)  │                  │
│     │ ────────────────────────► │                  │
│     │                            │                  │
│     │                  用公钥验证 r 是否正确          │
│     │                  正确 → 确信 Alice 拥有私钥     │
│     │                  但 Bob 无法从 r 推出私钥       │
└─────────────────────────────────────────────────────┘
```

## 五、安全注意事项

### 私钥保护

```
┌──────────────────────────────────────────────────────┐
│                    私钥保护层级                         │
│                                                        │
│  最高安全：HSM（硬件安全模块）                           │
│    → 私钥在专用硬件中生成和使用，永不导出                  │
│    → 银行、CA 机构使用                                  │
│    → 成本：数千至数万美元                                │
│                                                        │
│  高安全：智能卡 / YubiKey / TPM                         │
│    → 私钥存储在防篡改芯片中                              │
│    → 签名操作在芯片内完成                                │
│    → 成本：几十至几百美元                                │
│                                                        │
│  中等安全：加密的密钥文件 + 密码保护                      │
│    → 如 SSH 私钥用 passphrase 加密                      │
│    → 存储在磁盘上，用 AES 加密                           │
│                                                        │
│  低安全：明文存储的私钥文件                               │
│    → 极不推荐！                                         │
│    → 任何获得文件访问权限的人都能窃取                      │
└──────────────────────────────────────────────────────┘
```

### 常见攻击与防范

```
1. 中间人攻击 → 用数字证书(PKI)防范
2. 私钥泄露   → 证书吊销(CRL/OCSP) + 密钥轮换
3. 侧信道攻击 → 恒定时间算法实现
4. 量子威胁   → 迁移到后量子密码算法
5. 随机数不足 → 使用密码学安全随机数生成器(CSPRNG)
```
